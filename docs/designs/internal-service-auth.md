# Internal Service-to-Service Authentication

## 1. Summary

Today, `ms-inventario`, `ms-pedidos`, `ms-envios`, `ms-pagos`, and `notification-service` have **no authentication mechanism of their own** — none of their `pom.xml` files depend on `spring-boot-starter-security`, and none of their controllers inspect any credential. They are unreachable from the host (no published Docker port), but *within* `smartlogix-net` any container — including a compromised one — can call any of these services' endpoints directly, with the exact request the task calls out as the motivating example: `POST /pedidos/{id}/confirmar-pago`, which is supposed to be called only by `ms-pagos` after Flow confirms a payment, but today accepts a call from literally anything on the network, including a plain unauthenticated `curl` from another container.

This design adds a lightweight, symmetric **HMAC-SHA256 service-signature** scheme: every internal HTTP call (gateway → service, and service → service) carries three headers (`X-Internal-Service`, `X-Internal-Timestamp`, `X-Internal-Signature`) proving *which service* is calling and that the request is fresh (30s TTL). Each receiving service validates the signature with a shared secret (`INTERNAL_SERVICE_SECRET`, distinct from `JWT_SECRET`) and checks the caller against a **per-endpoint allowlist** of which services are legitimately allowed to invoke it. This directly closes the `confirmar-pago` example: after this change, that endpoint accepts calls only from a request signed by `ms-pagos` — not from `api-gateway`, not from `ms-inventario`, not from an unauthenticated caller.

This is additive to, and does not replace, the existing `X-User-Email` anti-spoofing header (which answers "which user") — it answers a different question ("which service"), and both are enforced independently on the same request where both apply.

## 2. Affected services

| Service | Change | Role |
|---|---|---|
| `api-gateway` | New `InternalTokenSigner` component; new `InternalTokenIssuerFilter` chained into every route that proxies to a downstream microservice; `DashboardController`'s three `WebClient`s get the same signer attached via an `ExchangeFilterFunction`. | **Issuer only** — never receives internal calls itself. |
| `ms-inventario` | New `InternalAuthFilter` (`jakarta.servlet.Filter`) validating all `/inventario/**` requests against a per-path issuer allowlist. New `pom.xml` entries: none needed (uses `javax.crypto.Mac`, already in the JDK). | **Receiver only** — makes no outbound calls. |
| `ms-envios` | Same `InternalAuthFilter` pattern, own per-path allowlist. | **Receiver only.** |

| `ms-pagos` | `InternalAuthFilter` on `/pagos/crear`, `/pagos/{id}`, `/pagos/por-token/{token}` (receiver). `/pagos/webhook/flow` is explicitly **excluded** — Flow Chile is an external caller that cannot hold `INTERNAL_SERVICE_SECRET`; it keeps relying on its own HMAC signature (`s` param, `FlowService.verificarFirmaWebhook`), unchanged. `PagoService`'s `RestTemplate` gets an `InternalAuthInterceptor` (`ClientHttpRequestInterceptor`) added for its two outbound calls to `ms-pedidos` (issuer). | **Both.** |
| `notification-service` | `InternalAuthFilter` on `POST /notificaciones`, allowlisting `ms-pedidos` only. | **Receiver only.** |
| `auth-service` | **No change.** Nothing calls it internally (confirmed: no service holds an `AUTH_URL`/reference to `auth-service` outside `api-gateway`'s public `/api/auth/**` route), and it makes no outbound calls to other services. Out of scope. | N/A |
| `frontend` | **No change.** This is entirely inside `smartlogix-net`; the browser never sees these headers (`api-gateway` both consumes the user's cookie and mints the internal headers on the same request, then forwards). | N/A |

**Coordination classification: independent parallel changes, not a Saga or a Facade.** There is no multi-step business transaction being introduced and no single service coordinating subsystems on behalf of a caller — this is a cross-cutting security control (comparable in shape to how the JWT-cookie migration was classified) applied consistently to seven independent call sites. The one piece of real coordination needed is that **all services must agree on `INTERNAL_SERVICE_SECRET` and the exact signing recipe** — this is a shared-contract risk, not a transactional one; see §9.

## 3. Mechanism chosen, and why not mTLS

**Chosen: shared-secret HMAC-SHA256 service signature**, transported as three plain HTTP headers, verified by each service against an env-var secret. Not a JWT library (no `jjwt` dependency added) and not mTLS.

**Why not mTLS**, explicitly, since the task asks for the tradeoff to be justified rather than assumed:
- mTLS would require: an internal CA, a certificate per service (7 certs), a distribution/mounting mechanism into each container, expiry/rotation handling, and either Spring Boot's SSL bundle support configured symmetrically on both server and `WebClient`/`RestTemplate` client sides in every one of the 7 services, or a sidecar/service-mesh (Envoy/Istio) — which this docker-compose, single-host, no-orchestrator deployment has no infrastructure for today.
- The actual threat this closes is "a compromised container on `smartlogix-net` calls another service directly." mTLS and a shared-secret HMAC scheme both fully close this threat *for the purpose of proving service identity* — mTLS additionally gives transport encryption, but this repo's internal traffic is already unencrypted HTTP by design (compliance doc §4.1 lists inter-service TLS as out of scope for this environment, same as the browser-facing TLS gap), so mTLS's main additional benefit (confidentiality/integrity in transit) isn't being purchased here either way; only its cost (cert lifecycle engineering) would be. That's a bad trade for a project at this stage.
- A shared-secret scheme is trivially demonstrable, testable, and reviewable by a reviewer/QA agent (one env var, one header set, no keystore/truststore machinery to get wrong), and it **directly reuses a pattern already implemented, tested, and audited in this exact codebase**: `ms-pagos`'s `FlowService.verificarFirmaWebhook`/`firmar` already does HMAC-SHA256 signing with `Mac.getInstance("HmacSHA256")` + `SecretKeySpec` + constant-time `MessageDigest.isEqual` comparison, and `COMPLIANCE_CL.md` §4.1 explicitly lists this exact recipe as `✅ confirmado en auditoría`. This design is that same recipe applied east-west instead of only on the Flow webhook's north-south path — not a new abstraction, an extension of one already trusted.
- **Rejected middle ground — a full internal JWT via `jjwt`**: would work, but `jjwt` is currently only a dependency of `auth-service` and `api-gateway`; adding it to the other 5 services purely to carry three claims (`iss`, `iat`, `exp`) that a raw HMAC-over-a-string already expresses is unnecessary dependency surface for no behavioral gain over the simpler scheme below.
- **If SmartLogix later moves to Kubernetes with a service mesh, or genuinely needs encryption-in-transit internally** (e.g., a real multi-tenant/regulated production deployment), mTLS (or mesh-provided mTLS) becomes the right call — flagged in Open Questions as the trigger condition to revisit, not proposed speculatively now.

**The recipe** (mirrors `FlowService.firmar`, adapted):
- `stringToSign = callingServiceName + ":" + timestampEpochMillis`
- `signature = HexFormat.of().formatHex(Mac.getInstance("HmacSHA256").doFinal(stringToSign.getBytes(UTF_8)))`, keyed with `INTERNAL_SERVICE_SECRET.getBytes(UTF_8)` via `SecretKeySpec`.
- Headers set on every internal outbound request: `X-Internal-Service: <callingServiceName>`, `X-Internal-Timestamp: <timestampEpochMillis>`, `X-Internal-Signature: <hex>`.
- **Deliberately not bound to method+path.** An earlier draft of this design considered `stringToSign = service + ts + method + path` for tighter scoping, but this was rejected: the exact literal path string differs depending on where in the Spring Cloud Gateway MVC filter chain (`stripPrefix` vs not) the header is minted vs. checked, which is exactly the kind of fragile, non-obvious plumbing detail that should not be load-bearing for a security control. The simpler `service:timestamp` string, combined with (a) a 30-second TTL and (b) a per-endpoint issuer allowlist enforced server-side (§4), gives the security property that matters ("only `ms-pagos` can hit `confirmar-pago`") without depending on both ends agreeing on an unverified-in-this-design path representation.
- `callingServiceName` is a hardcoded constant per service (`"api-gateway"`, `"ms-pedidos"`, `"ms-pagos"`) — not configurable, not read from a header, so a compromised service can claim to be itself but cannot relabel itself as another service without knowing the shared secret to produce a valid signature for that claim.

**New env var: `INTERNAL_SERVICE_SECRET`.** Following the existing convention (`JWT_SECRET`, `DB_PASS`): no hardcoded default anywhere, service fails to start (or the filter fails closed, rejecting every request — see §8) if unset. Must be a **different value from `JWT_SECRET`** — reusing the same secret would mean every one of the 5 downstream services holds the same key material used to sign user-facing JWTs, which is unnecessary blast-radius expansion for no benefit (these two credentials protect different trust boundaries: "who is the human user" vs. "which internal process is calling"). Generate the same way as `DB_PASS` (`openssl rand -base64 32`).

## 4. Interaction with the Saga orchestrator specifically

`SagaOrchestrator` itself needs **zero changes** — it calls `SagaStep.execute()`/`compensate()` on `InventarioSagaClient`/`CreateShipmentStep`/`NotifyStep`, and the internal-auth headers are added one layer down, inside each `WebClient` call, transparently to the orchestration logic. Concretely:

- `InventarioSagaClient.reservarStock`/`liberarStock` (forward step + compensation step alike) get the `ExchangeFilterFunction` on their `WebClient`. **Compensation calls are signed exactly like forward calls** — there is no special-casing needed, because the receiving `InternalAuthFilter` in `ms-inventario` doesn't distinguish "is this a forward step or a compensation" (it never did, and doesn't need to — it just checks "is the caller `ms-pedidos`").
- `EnviosSagaClient.crearEnvio`/`cancelarEnvio` — same treatment.
- `NotifyStep` — same treatment; note this step already swallows all failures (`SagaStepException` is deliberately never thrown here per the existing "non-critical" comment) — a missing/invalid internal-auth response from `notification-service` (e.g., during rollout if `notification-service` is upgraded before `ms-pedidos`, see §9) degrades to "notification not sent, Saga still succeeds," identical to today's behavior for any other `notification-service` failure. No new failure mode is introduced for this step.
- **Retry/failure semantics are unchanged.** If a saga step's outbound call now fails with `401`/`403` because signing is misconfigured (e.g., mismatched secret across services), `InventarioSagaClient`'s/`EnviosSagaClient`'s existing `@CircuitBreaker` fallback methods (`reservarFallback`, `crearFallback`, etc.) fire exactly as they do for any other HTTP failure today, which throws and causes `SagaOrchestrator` to run compensations in reverse order — i.e., a misconfigured internal secret fails safe into the existing compensation path, it does not silently proceed. This is a meaningful operational property worth calling out: a secret-rotation mistake degrades to "sagas fail and compensate" (loud, visible, recoverable), not "requests silently succeed unauthenticated" or "requests silently succeed with a stale credential."
- The **webhook-initiated call** (`ms-pagos.PagoService.confirmarPagoEnPedidos` → `ms-pedidos`'s `POST /pedidos/{id}/confirmar-pago`, which is what triggers the Saga in the first place via `OrderService.confirmarPagoYDispararSaga`) is a *service-initiated* call outside the Saga's own step list, but uses the identical mechanism: `ms-pagos` signs as `"ms-pagos"`, `ms-pedidos`'s `InternalAuthFilter` allowlists `ms-pagos` (and only `ms-pagos`) for that specific path. This is the exact call named in the compliance gap, and it's the one that actually *triggers* the Saga, so it's the most important single edge case to test end-to-end (see Acceptance Criteria #12).

## 5. API contract

Convention addition to the existing rule ("all endpoints require `Authorization: Bearer <token>`... except `/api/auth/*` and `/api/pagos/webhook/flow`"): **all endpoints on `ms-inventario`, `ms-pedidos`, `ms-envios`, `ms-pagos` (except `/pagos/webhook/flow`), and `notification-service` additionally require the three internal-auth headers below, checked against a per-service, per-path issuer allowlist.** This is enforced *inside* the docker network, in addition to (not instead of) the existing gateway-level user JWT check for the routes the gateway proxies.

### 5.1 New headers (required on every internal call, both gateway→service and service→service)

| Header | Format | Set by |
|---|---|---|
| `X-Internal-Service` | one of `api-gateway`, `ms-pedidos`, `ms-pagos` (the only three services that ever act as callers) | The calling service, hardcoded constant |
| `X-Internal-Timestamp` | epoch milliseconds, string | The calling service, freshly generated per outbound call (not cached/reused) |
| `X-Internal-Signature` | lowercase hex, `HMAC-SHA256(INTERNAL_SERVICE_SECRET, X-Internal-Service + ":" + X-Internal-Timestamp)` | The calling service |

**Anti-spoofing requirement, mirroring the existing `X-User-Email` strip-then-set pattern in `AuthFilter`:** `api-gateway`'s new `InternalTokenIssuerFilter` must strip any client-supplied `X-Internal-Service`/`X-Internal-Timestamp`/`X-Internal-Signature` headers before setting its own, on every route it proxies. (Note: even without this stripping, a forged header from outside would fail signature verification since an external caller doesn't know `INTERNAL_SERVICE_SECRET` — but stripping is required anyway as defense-in-depth and to keep the security posture consistent and reviewable, not "safe only because of a property that happens to also hold.")

### 5.2 Per-service, per-path issuer allowlist (the actual access-control decision)

| Service | Path(s) | Allowed `X-Internal-Service` value(s) |
|---|---|---|
| `ms-inventario` | `POST /inventario/{id}/reservar`, `POST /inventario/{id}/liberar`, `GET /inventario/{id}/stock` | `ms-pedidos` only |
| `ms-inventario` | everything else (`GET/POST /inventario`, `GET/PUT/DELETE /inventario/{id}`, `/alertas`, `/alertas/estrategia`, `/alertas/estrategias`, `/health`) | `api-gateway` only |
| `ms-envios` | `DELETE /envios/{id}/cancelar` | `ms-pedidos` only |
| `ms-envios` | `POST /envios` | `api-gateway` or `ms-pedidos` (both a user-initiated create and the Saga's `CreateShipmentStep` hit this path) |
| `ms-envios` | everything else (`GET /envios`, `GET /envios/{id}`, `PATCH /envios/{id}/status`, `/health`) | `api-gateway` only |
| `ms-pedidos` | `POST /pedidos/{id}/confirmar-pago`, `POST /pedidos/{id}/pago-fallido` | `ms-pagos` **only** — this is the exact endpoint named in the compliance gap; `api-gateway` is explicitly **not** on this allowlist even though its `/api/pedidos/**` route physically proxies to this path today |
| `ms-pedidos` | everything else (`POST/GET /pedidos`, `GET /pedidos/{id}`, `/pedidos/health`, `/sagas/**`) | `api-gateway` only |
| `ms-pagos` | `POST /pagos/crear`, `GET /pagos/{id}`, `GET /pagos/por-token/{token}` | `api-gateway` only |
| `ms-pagos` | `POST /pagos/webhook/flow` | **N/A — excluded from `InternalAuthFilter` entirely**, keeps existing Flow HMAC signature check |
| `notification-service` | `POST /notificaciones` | `ms-pedidos` only |
| `notification-service` | `GET /notificaciones/health` | `ms-pedidos` only (nothing else calls it internally; if a container healthcheck is added later, exempt it explicitly at that time rather than widening this now — see §9) |

This table is the actual deliverable a developer implements as a small `Map<RequestMatcher-like-pattern, Set<String>>` (or an equivalent `if/else` on `request.getMethod()`/`getRequestURI()`) inside each service's `InternalAuthFilter` — precise enough that "which services can call which path" is not left to the implementer's judgment.

### 5.3 Error responses (new, uniform across all five receiving services)

| Condition | Status | Body |
|---|---|---|
| Any of the 3 headers missing | `401` | `{"error": "Autenticación interna requerida"}` |
| `X-Internal-Timestamp` not parseable as a long | `401` | `{"error": "Autenticación interna inválida"}` |
| `abs(now - timestamp) > 30000` ms | `401` | `{"error": "Credencial interna expirada"}` |
| Signature does not match (constant-time compare, `MessageDigest.isEqual`) | `401` | `{"error": "Firma interna inválida"}` |
| Signature valid, but `X-Internal-Service` is not on the allowlist for the requested path | `403` | `{"error": "Servicio no autorizado para este recurso"}` |
| `INTERNAL_SERVICE_SECRET` unset/blank at startup | Service **fails to start** (mirrors `JWT_SECRET`/`DB_PASS` convention — no silent fallback, no filter that "passes everything through" if misconfigured) | N/A |

This filter runs **before** the existing controller logic on every request (standard Servlet `Filter`, registered with `@Order` early, or a `FilterRegistrationBean` with the lowest precedence) — it is a hard gate, not best-effort.

## 6. Data model changes

**None, for any of the 7 service databases.** This design is entirely stateless: no nonce table, no replay cache, no revocation list, no persisted service-identity registry. The allowlist is a compile-time constant per service (§5.2), not configuration data, so there's nothing to migrate. This keeps the design consistent with the existing stateless-JWT posture already accepted for user auth (per `jwt-httponly-cookie-migration.md` §4) and avoids introducing new shared infrastructure (e.g., Redis for a nonce cache) that nothing else in this stack currently needs — see §9 for the explicit tradeoff on replay protection this implies.

## 7. Design pattern fit

This extends two patterns already present and audited in this codebase, rather than introducing a new one:

1. **HMAC signature verification** (`ms-pagos`'s `FlowService.verificarFirmaWebhook`) — same primitive (`Mac.getInstance("HmacSHA256")`, `SecretKeySpec`, `MessageDigest.isEqual` constant-time compare), applied to a new set of callers. README's pattern table already lists "Flow Payment Gateway... firma HMAC-SHA256" as an existing integration pattern; this design is the same cryptographic building block reused for internal traffic, not a new category.
2. **The `AuthFilter` strip-then-set anti-spoofing convention** (API Gateway pattern) — `InternalTokenIssuerFilter` in `api-gateway` and each service's `InternalAuthFilter` follow the identical shape already established for `X-User-Email`: never trust a client-supplied identity header, always derive and overwrite it from a verified source.

No new GoF pattern (Strategy, Observer, Factory, etc.) is introduced, and a shared library module is deliberately **not** created even though the `InternalAuthFilter` logic is near-identical across 5 services — per the task's explicit constraint, this repo has no shared-module precedent, and introducing one now (with the versioning/build-coordination overhead of a multi-module Maven reactor change across `pom.xml`s that don't currently reference each other) would be a bigger structural change than the security control itself warrants. The ~40 lines of filter code are duplicated 5 times; this is treated as acceptable, explicit duplication (each copy is small, reviewable independently, and the copies are expected to diverge slightly anyway — the allowlist in §5.2 is different per service).

## 8. Security requirements (OWASP Top 10 2021)

**A01 — Broken Access Control.** This is the core of the design. Today: any container on `smartlogix-net` can call any endpoint on the 5 unprotected services with zero credentials. After this change: a caller must (a) hold `INTERNAL_SERVICE_SECRET` to produce any valid signature at all, and (b) be on the specific path's allowlist. This closes the literal example in the compliance gap (`POST /pedidos/{id}/confirmar-pago` now rejects everything except a request signed as `ms-pagos`) and generalizes it to every Saga-compensation and payment-adjacent endpoint (§5.2). Explicitly **not** an ownership/tenant check on a resource ID — this is service identity, not user identity; per `COMPLIANCE_CL.md` §4.1, SmartLogix's domain is confirmed single-tenant with no per-user ownership model on `Pedido`/`Envio`/`Pago` records, so there is no IDOR-class check to add on top of this at the resource level — this was independently confirmed in the prior security audit and is unchanged by this feature.

**A02 — Cryptographic Failures.** `INTERNAL_SERVICE_SECRET` is a new secret; it must follow the exact same handling convention as `JWT_SECRET`/`DB_PASS` (env var only, no default, not logged — see A09). It is a distinct value from `JWT_SECRET` (§3) to avoid blast-radius sharing between the user-auth trust boundary and the internal-service trust boundary. No payment card data or PII flows through these new headers — they carry only a service name and a timestamp.

**A03 — Injection.** N/A. No new SQL, dynamic queries, or shell construction. The three header values are parsed as a fixed-format string (service name against a hardcoded enum, timestamp as `Long.parseLong`), never interpolated into a query or command.

**A04 — Insecure Design (abuse cases).**
- **Retry:** idempotent by nature — an internal call retried with a *freshly signed* set of headers (new timestamp, new signature) is valid; retrying with the *exact same* headers within the 30s window would also currently succeed (see replay note below), but the downstream business operations being protected (`reservarStock`, `confirmarPago`, etc.) already have their own idempotency handling independent of this feature (`PagoService.procesarWebhook` already checks `pago.getEstado()` before reprocessing; `confirmarPago` re-triggering the Saga on a genuine retry is a pre-existing concern this design doesn't change).
- **Replay window (accepted residual risk, stated explicitly rather than silently accepted):** a captured, valid set of the three headers remains valid for the remainder of its 30-second window and is not bound to a specific request path/body (§3 explains why path-binding was rejected). Within `smartlogix-net`, capturing another container's traffic requires an attacker to already have a foothold with packet-sniffing capability on the Docker bridge network — a materially more privileged position than "can send one HTTP request" — so this is judged an acceptable residual risk for the current threat model (no external network access, ports closed per the prior audit). A nonce-based replay cache would close this fully but requires shared state (Redis) that doesn't exist in this stack today and would be disproportionate infrastructure for this residual risk — explicitly deferred, not silently skipped (see §9).
- **Race condition:** no new race is introduced — the signature check is a pure, stateless computation per request; nothing here changes any existing Saga compensation race behavior.

**A05 — Security Misconfiguration.** New env var `INTERNAL_SERVICE_SECRET` required in `api-gateway`, `ms-pedidos`, `ms-pagos` (issuers), `ms-inventario`, `ms-envios`, `notification-service` (receivers) — must be added to `docker-compose.yml`'s `environment:` block for each, and documented in README's "Variables de entorno" table alongside `JWT_SECRET`/`DB_PASS`. No new ports, no new actuator exposure — Actuator endpoints on the 5 services are **not** currently exempted from `InternalAuthFilter` in this design (the filter is registered broadly); if a container healthcheck referencing `/actuator/health` is added in the future, it must be explicitly exempted at that time rather than pre-emptively widening the allowlist now for a healthcheck that doesn't exist yet in `docker-compose.yml` today.

**A07 — Auth Failures.** This is additive to, not a replacement for, the existing JWT/cookie-based user authentication at `api-gateway`. No change to `JwtUtil`, `AuthFilter`'s cookie handling, or session lifecycle.

**A08 — Software/Data Integrity.** The signature check is exactly what prevents a request's claimed service identity (`X-Internal-Service`) from being tampered with in transit without detection — this is new integrity protection on the internal network path that didn't exist before. No deserialization of external input is introduced (three plain string/long headers, no object graph).

**A09 — Logging/Monitoring.** **Must log:** every rejected internal-auth attempt (missing headers, expired timestamp, bad signature, disallowed issuer) at `WARN`/`ERROR` with the claimed `X-Internal-Service` value, the path, and a timestamp — these are exactly the "servicio comprometido llamando sin credenciales" events `COMPLIANCE_CL.md` §4.3/§4.4 cares about being able to reconstruct for an incident. **Must NOT log:** `INTERNAL_SERVICE_SECRET` itself, or the full `X-Internal-Signature` value in plaintext in routine (non-error) logs — if signature values are logged for debugging a rejection, mask them (same convention as the Flow token masking already in `PagoService`, `token.substring(0,8)+"***"`).

**A10 — SSRF.** N/A. The URLs called (`INVENTARIO_URL`, `PEDIDOS_URL`, `ENVIOS_URL`, `NOTIFICATION_URL`, `PAGOS_URL`) are all fixed, operator-configured env vars — none are built from user input, unchanged by this design.

## 9. Chilean compliance touchpoints

Per `docs/COMPLIANCE_CL.md` §4.1, this design directly closes the row: *"Autenticación servicio-a-servicio interna (mTLS o JWT de servicio) — ❌ pendiente."* Once implemented, that row should move to `✅ implementado` with a description along the lines of "firma HMAC-SHA256 simétrica (`X-Internal-Service`/`X-Internal-Timestamp`/`X-Internal-Signature`), verificada por servicio con allowlist de emisor por endpoint," citing the merging commit/PR, per §5 of that document's own instructions to the reviewer.

- **Ley 21.663 (gestión de riesgos / detección de incidentes):** the new rejection logging (§8, A09) is a concrete, direct improvement to the "capacidad técnica de detectar, registrar y escalar un incidente rápido" goal called out in `COMPLIANCE_CL.md` §3 — a burst of `403`/`401` internal-auth rejections against, say, `ms-pedidos`'s `confirmar-pago` path from an unexpected source is now a detectable, loggable signal of a potentially compromised container, where today it would be indistinguishable from normal traffic.
- **Ley 21.719 (deber de seguridad):** this is a "medida técnica proporcional al riesgo" improvement to the internal handling of personal data that flows through these services (nombre/email/destino per §2 of the compliance doc) — it reduces the blast radius of a single compromised container being able to read/write another service's data (e.g., a compromised `ms-inventario` container could not use this vector to force `ms-pedidos` to disclose or mutate order data it has no legitimate reason to touch).
- **ARCO+ rights (§4.2):** not affected — no new personal data field is created, exposed, or retained by this feature; the new headers carry only a service name and timestamp, never personal data.
- **Retention (§4.4):** N/A — no new persisted data (§6), nothing to retain or purge under a retention policy.

## 10. Acceptance criteria

1. A request to any protected endpoint on `ms-inventario`/`ms-pedidos`/`ms-envios`/`ms-pagos`(non-webhook)/`notification-service` **with none of the three internal-auth headers** returns `401` with the "Autenticación interna requerida" body, and the underlying business logic is never invoked (verifiable: no DB row written, no downstream call made).
2. Same as #1, but with a **syntactically well-formed but wrong-signature** `X-Internal-Signature` (i.e., a random hex string of the correct length) → `401` "Firma interna inválida."
3. Same as #1, but with a **valid signature computed for a timestamp more than 30 seconds old** → `401` "Credencial interna expirada."
4. Same as #1, but with a **valid signature and fresh timestamp, claiming `X-Internal-Service: ms-inventario`**, sent to `ms-pedidos`'s `POST /pedidos/{id}/confirmar-pago` → `403` "Servicio no autorizado para este recurso" (proves the per-path allowlist rejects a technically-valid-but-wrong-issuer credential — this is the literal regression test for the compliance gap's named example).
5. A request to `ms-pedidos`'s `POST /pedidos/{id}/confirmar-pago` with a **valid signature claiming `X-Internal-Service: ms-pagos`** succeeds (`200`) and triggers the Saga, as today.
6. A request to `ms-pedidos`'s `POST /pedidos/{id}/confirmar-pago` with a **valid signature claiming `X-Internal-Service: api-gateway`** is rejected with `403`, even though `api-gateway`'s `/api/pedidos/**` route physically proxies to this exact path — proving the gateway itself cannot reach this endpoint despite being a generally-trusted issuer elsewhere.
7. ## 11. Open questions

1. **Clock synchronization assumption.** The 30-second TTL assumes all 7 containers share a clock (true today: single-host Docker Compose, all containers use the host clock). If SmartLogix ever moves to a multi-host deployment (Swarm/Kubernetes across nodes), clock skew between hosts could cause spurious `401`s on legitimate calls — worth a one-line acknowledgment from whoever owns that future migration, not a blocker now.
2. **TTL value (30s).** Chosen as "generous enough to never cause a false rejection under normal load/latency, short enough to bound the accepted replay-window risk in §8 A04" — not empirically tuned. If reviewer/QA observes flakiness under slow CI/test conditions (e.g., a `WebClient` call queued behind a slow DB write before it's sent), this may need to be widened; recommend starting at 30s and revisiting only if evidence warrants it, rather than guessing higher upfront.
3. **`ms-envios`'s `POST /envios` dual-issuer allowlist** (§5.2) — confirmed by reading `EnvioController`/`EnviosSagaClient` that both a user-facing create and the Saga's `CreateShipmentStep` hit this exact path today. If a future design wants to distinguish "user-created shipment" from "Saga-created shipment" at the business-logic level (e.g., different default fields), that's a separate, larger change than this design's scope — flagging so it isn't confused with an oversight here.
4. **Should `INTERNAL_SERVICE_SECRET` absence be a hard startup failure or a runtime-checked property?** `JWT_SECRET` fails at Spring context startup because it's bound via `@Value` with no default into a bean that's exercised immediately. Whether the developer agent implements the same "fail at startup" behavior for `INTERNAL_SERVICE_SECRET` (cleaner, fails loud immediately) or a "fail every request at runtime" behavior (also acceptable, per acceptance criterion #13) is left as an implementation choice, but it must be the **same choice across all 6 affected services** for consistency — flagging so the developer agent doesn't implement it two different ways in two different services.
5. **Not addressed by this design, flagged as a related but distinct follow-up:** `api-gateway`'s `/api/pedidos/**` route still physically proxies user JWT-authenticated traffic to `confirmar-pago`/`pago-fallido` (it's just that `ms-pedidos` now rejects it with `403` because the issuer is `api-gateway`, not `ms-pagos`). This design closes the *service-identity* gap correctly and completely (criterion #6), but a cleaner architecture would also exclude these two paths from the gateway's routable surface entirely (e.g., a narrower route predicate) so that a user-authenticated request to that path fails at the gateway with a clear `404`/`403` instead of reaching `ms-pedidos` and being rejected there. Not proposed as in-scope here since it's a `GatewayConfig` routing change orthogonal to internal service auth, but worth a fast-follow ticket.

## QA feedback (iteration 1)

**VERDICT: FAIL — IMPLEMENTATION BUG, route back to developer.**

Acceptance criterion #13 is violated in practice, not just in ambiguity. Live-tested with `INTERNAL_SERVICE_SECRET` absent from `.env` (the realistic misconfiguration — Docker Compose substitutes an empty string, with a warning, rather than leaving the variable unset): all 6 affected services (`api-gateway`, `ms-inventario`, `ms-pedidos`, `ms-envios`, `ms-pagos`, `notification-service`) **start successfully** — no fail-fast — and then throw an unhandled `IllegalArgumentException: Empty key` from `new SecretKeySpec("".getBytes(), "HmacSHA256")` the first time `InternalAuthFilter.sign()` / the equivalent issuer-side signer or interceptor runs. This surfaces as a raw, unhandled `500 Internal Server Error` on every request — not a clean startup failure, and not the uniform 401 "Autenticación interna inválida" the error contract in §5.3/§8(A05) specifies. It doesn't leak the stack trace and doesn't let anything through unauthenticated (functionally still fail-closed), but it violates the letter of the criterion and diverges from this exact codebase's own established precedent: `JwtUtil.isValid` catches exceptions from a blank/invalid `JWT_SECRET` internally and returns `false`, producing a clean 401 — `INTERNAL_SERVICE_SECRET` should mirror that pattern, not throw past it.

Required fix, applied identically across all 6 services (pick one approach, not a mix, per open question #4):
- Either: fail fast at startup with a clear `IllegalStateException` when the secret is blank/null (e.g. in a `@PostConstruct` on whichever bean owns the secret), matching how `JWT_SECRET`/`DB_PASS` behave today, **or**
- Catch the signing/verification exception at the point of use and translate it into the standard rejection response (401, same JSON error body as every other rejection reason), so a blank secret degrades identically to "credential invalid" from the caller's perspective.

All other 14 acceptance criteria passed live testing (every abuse case — missing headers, forged signature, expired TTL, wrong-issuer-on-locked-endpoint, gateway-cannot-reach-confirmar-pago — plus the full Saga forward and compensation paths with internal-auth enforced at every hop, the Flow webhook exclusion, and zero regressions in the JWT cookie auth or anti-spoofing behavior from the prior cycle). This should be a scoped, quick fix and re-verification, not a broad re-test.
