# ARCO+ Derechos Restantes — Cancelación y Oposición

## 1. Summary

`docs/COMPLIANCE_CL.md` §4.2 lists Acceso (`arco-acceso-personal-data.md`), Rectificación, and Portabilidad (`arco-remaining-rights.md`) as `✅ implementado`, and Cancelación/Oposición as `❌ pendiente`, explicitly deferred by `arco-remaining-rights.md` §9 (points 3–4) to "a dedicated design cycle." This document is that cycle. It makes the four calls that document's handoff notes left open, verified against the actual entity classes and orchestration code (not assumed), and designs both rights to the same rigor as the two prior cycles.

**Cancelación** is implemented as a **Facade-orchestrated, idempotent, forward-only state transition** — not a Saga (no compensation semantics fit "erasure": there is no meaningful "undo" of an anonymized row) and not a new message-broker/outbox (this stack has zero infrastructure for either, and none is needed). `api-gateway` remains the single coordinator, exactly as it already is for `GET /api/usuarios/me/datos` and `PUT /api/usuarios/me/email`. Reading the actual entities surfaced an important correction to the prior doc's handoff assumption: **`Envio` holds no personal data belonging to the SmartLogix account holder at all** (only `pedidoId`, a logical FK, and `destino`, which is the *PYME's own end customer's* shipping address — a different data subject entirely, per `Pedido.clienteNombre`'s own comment "Nombre del cliente final de la PYME"). So `ms-envios` needs **zero** anonymization code — only `ms-pedidos` (`Pedido.userEmail`) and `ms-pagos` (`Pago.email`) actually store the account holder's own identifying data outside `auth-service`. This is a materially smaller blast radius than the prior doc assumed, discovered by reading the code rather than guessing.

**Oposición** is implemented as a real, minimal, honestly-scoped mechanism: a durable `oposicionProcesamiento` boolean + timestamp on `User`, settable via a genuine new endpoint (`POST /api/usuarios/me/oposicion`), exposed back to the user via the existing acceso/portabilidad aggregation. Re-grepping the codebase (marketing/analytics/profiling/newsletter/opt-in/opt-out/tracking-consent/publicidad/segmentación) confirms the prior finding still holds: **no optional or legitimate-interest processing exists today** — `notification-service` is a stateless pass-through stub (`NotificationListener.recibirNotificacion` only logs the payload and returns `200`; it doesn't even send an email) triggered exclusively by `ms-pedidos`'s Saga for contract-necessary logistics events. Given that, and given the user has explicitly asked for this to be built now, this design is honest about what the flag does: **it currently gates zero processing**, because there is genuinely nothing eligible to gate (blocking transactional/contract-necessary notifications on this flag would be a compliance *mistake*, not a feature — Ley 21.719's derecho de oposición applies to legitimate-interest/optional processing, not to processing necessary to execute the contract the user is actively using). Its value today is (a) a durable, audited record that the data subject exercised this right on a specific date — itself a concrete accountability improvement — and (b) a structural checkpoint that any future optional-processing feature (marketing email, analytics, profiling) is required to consult before this design's acceptance criteria can be considered satisfied for that future feature.

**Coordination classification.**
- **Cancelación**: a **Facade** (`api-gateway` as single coordinator, same role `UsuarioDatosController` already plays) driving a **persisted, idempotent, forward-only state machine** on `User.status` (`ACTIVA → CANCELACION_EN_PROGRESO → CANCELADA`). This is explicitly **not** the `SagaOrchestrator` pattern: that class is parameterized on `CreatePedidoRequest`/`SagaStep` for order creation specifically, and — more fundamentally — its entire reason to exist is running compensations in reverse order when a forward step fails; there is no meaningful compensation for "a row was anonymized" (you cannot un-anonymize data you didn't keep a copy of, and keeping a copy defeats the purpose of anonymizing). The correct failure semantics here are "retry the same idempotent forward operation until every service confirms," which is what this design does, using Reactor's built-in retry operator rather than introducing Resilience4j into a service that doesn't have it, or a new persistence-backed job queue this stack has no precedent for.
- **Oposición**: a single-service mutation (`api-gateway` → `auth-service`, one write, no compensation needed) — the same shape already classified for Rectificación, not a Saga or Facade.

## 4. Data model changes

| Service | Change |
|---|---|
| `auth_db` (`auth-service`) | New nullable columns on `users`: `status VARCHAR` (`ACTIVA`/`CANCELACION_EN_PROGRESO`/`CANCELADA`; `NULL` on pre-existing rows treated as `ACTIVA` in code — same "no backfill" convention already accepted for `created_at`, `ddl-auto=update`, no Flyway/Liquibase in this repo), `cancelacion_solicitada_en TIMESTAMP`, `cancelacion_completada_en TIMESTAMP`, `oposicion_procesamiento BOOLEAN` (nullable `Boolean` wrapper, not primitive — same nullable-add-to-populated-table reasoning as `created_at`; `NULL` treated as `false` in code), `oposicion_registrada_en TIMESTAMP`. |
| `pedidos_db` (`ms-pedidos`) | **No schema change.** `Pedido.userEmail` already exists; only a new bulk-`UPDATE` repository method. |
| `pagos_db` (`ms-pagos`) | **No schema change.** `Pago.email` already exists; only a new bulk-`UPDATE` repository method. |
| `envios_db` (`ms-envios`) | **No change of any kind** — no schema change, no code change (§3). |

No cross-service joins/foreign keys introduced, consistent with database-per-service. No new tables (no outbox/retry-ledger table) — the 3-state `status` column on the single `users` row already being mutated *is* the durable retry-state; no separate ledger is needed because there is exactly one row per cancelación request and its own status field is sufficient to know what to do on retry (§5).

### 4.1 Anonymization markers (exact values, chosen to avoid new unique-constraint conflicts)

- `pedidos_db.pedidos.user_email` → `"USUARIO_ELIMINADO"` (no unique constraint on this column — confirmed by reading `Pedido.java` — a shared marker across all cancelled accounts is safe).
- `pagos_db.pagos.email` → `"USUARIO_ELIMINADO"` (same — no unique constraint, confirmed by reading `Pago.java`).
- `auth_db.users.email` → `"usuario-eliminado-" + id + "@smartlogix.invalid"` — **must** be unique per row, since `users.email` has a `unique` constraint; `.invalid` is the RFC 2606-reserved TLD for exactly this "definitely not a real, deliverable address" use, and using the row's own numeric `id` (a surrogate key, not PII) guarantees uniqueness deterministically without needing a random suffix.
- `auth_db.users.password` → `passwordEncoder.encode(UUID.randomUUID().toString())` — a fresh BCrypt hash of an unrecoverable random value, so login remains impossible even if the `status` check were somehow bypassed (defense in depth, §6 A07).

## 5. Design pattern fit

**Cancelación** extends two patterns already audited in this codebase and introduces one new, narrowly-scoped mechanism, justified below:

1. **BFF/Facade aggregation** (`UsuarioDatosController`, `RectificacionController` precedent) — `CancelacionController` lives in `api-gateway`, reached via the existing `usuariosRoute()`, signs outbound calls via the existing `InternalTokenSigner.exchangeFilter()`. The blocking-check step reuses `UsuarioDatosController`'s exact two-hop read shape (pedidos-by-email, then envíos-by-pedido-ids) — **duplicated, not extracted into a shared helper**, consistent with this codebase's already-accepted stance on small, independently-reviewable duplication over premature shared abstraction (`internal-service-auth.md` §7, `arco-remaining-rights.md` §6 pt. 4).
2. **Repository pattern** — `anonimizarPorEmail` on `OrderRepository`/`PagoRepository` are ordinary `@Modifying @Query` bulk updates, the same JPA repository abstraction already used everywhere, applied to a write instead of a read for the first time in an ARCO+ cycle.
3. **New, narrow mechanism: a persisted 3-state idempotent lifecycle, not a new GoF pattern.** `User.status` (`ACTIVA → CANCELACION_EN_PROGRESO → CANCELADA`) is structurally similar to `ms-pedidos`'s own `SagaEstado.EstadoSaga` (`INICIADA/EN_PROGRESO/COMPENSANDO/COMPLETADA/FALLIDA`) in spirit — both are "a persisted status field tracking a multi-step operation" — but this design deliberately does **not** reuse `SagaOrchestrator` itself (§3, coordination classification) because that class's core contract (steps + compensations, parameterized on `CreatePedidoRequest`) doesn't fit an operation with no compensation. Introducing a *generic* Saga abstraction (decoupled from order creation) purely for this one feature would be a bigger structural change than the feature warrants — explicitly avoided as speculative abstraction the task's own ground rules warn against. The retry mechanism itself (Reactor's `retryWhen(Retry.backoff(...))`) is not new library surface: `reactor-core` is already a transitive dependency of every `WebClient` call in this gateway.

**Oposición** extends exactly the pattern Rectificación already established: `OposicionController` (api-gateway) → `PUT /auth/interno/usuarios/{email}/oposicion` (auth-service), same BFF shape, same internal-HMAC-auth reuse, no new pattern.

## 6. API contract

Convention (unchanged): all endpoints require the `sl_jwt` httpOnly cookie except `/api/auth/*` and `/api/pagos/webhook/flow`. New internal-only paths are excluded from public gateway routing exactly like every prior internal endpoint (§3).

### 6.1 `POST /api/usuarios/me/cancelacion` — new (Cancelación)

- Auth: valid `sl_jwt` cookie. Identity derived **exclusively** from the cookie, never from body/path — same anti-IDOR property as every prior ARCO+ mutation endpoint.
- Request body (required on **every** call, including retries of a stuck request — no conditional/reduced-body retry path, for contract simplicity):
  ```json
  { "passwordActual": "su-contraseña-actual", "confirmacion": "ELIMINAR_MI_CUENTA" }
  ```
  Validation: `passwordActual` — `@NotBlank`; `confirmacion` — `@NotBlank`, and must **exactly** (case-sensitive) equal the literal string `"ELIMINAR_MI_CUENTA"` (checked in the controller, not Bean Validation, so the error message can be specific and non-generic).
- **Step 1 (step-up-auth + state transition):** gateway calls `PUT /auth/interno/usuarios/{email}/cancelacion/iniciar`. `auth-service`: `findByEmail(email)` → `404` if not found (cookie-outlives-account edge case, or the account is already `CANCELADA` — its email column no longer matches `email`, so this naturally 404s, same as rectificación's existing edge case, no special-case code needed). Verify `passwordActual` → `401` if wrong. Verify `status` is `null`/`"ACTIVA"`/`"CANCELACION_EN_PROGRESO"` (idempotent: a retry of an in-progress cancelación is allowed and **preserves** the original `cancelacionSolicitadaEn`) — sets `status = "CANCELACION_EN_PROGRESO"`, sets `cancelacionSolicitadaEn = now()` **only if it was null**.
- **Step 2 (blocking-condition check, re-run on every call including retries):** gateway calls `GET /pedidos/interno/por-email/{email}` then, if non-empty, `GET /envios/interno/por-pedidos?pedidoIds=...` (identical shape to `UsuarioDatosController.agregarDatos`). Terminal-status **allowlists** (default-deny for anything not listed):
  - `Pedido.status` terminal (safe): `{"ENTREGADO", "CANCELADO", "PAGO_RECHAZADO", "PAGO_ANULADO"}`. Anything else (including `"PENDIENTE"`, `"PAGADO"`, `"CONFIRMADO"`, and any future/unrecognized value) **blocks**.
  - `Envio.status` terminal (safe): `{"ENTREGADO", "CANCELADO"}`. Anything else (`"CREADO"`, `"ASIGNADO"`, `"EN_RUTA"`, unrecognized) **blocks**.
  - If blocked: gateway calls `PUT /auth/interno/usuarios/{email}/cancelacion/revertir` (resets `status` to `"ACTIVA"`, clears `cancelacionSolicitadaEn`) and returns `409` (see below) **without** touching any pedido/pago data.
- **Step 3 (anonymization, only if not blocked):** gateway calls, in parallel, `PUT /pedidos/interno/por-email/{email}/anonimizar` and `PUT /pagos/interno/por-email/{email}/anonimizar`, each wrapped in `.retryWhen(Retry.backoff(3, Duration.ofMillis(300)))`. Both are idempotent bulk updates (already-anonymized rows simply don't match the `WHERE` clause on a retry — no double-application risk).
- **Step 4 (finalize, only if step 3 fully succeeded):** gateway calls `PUT /auth/interno/usuarios/{email}/cancelacion/finalizar` (auth-service sets the anonymized email/password per §4.1, `status = "CANCELADA"`, `cancelacionCompletadaEn = now()`). Gateway clears the `sl_jwt` cookie (`Set-Cookie` with `Max-Age=0`, same shape as `AuthController.logout`) and returns `200`.
- **If step 3 fails after retries are exhausted:** gateway does **not** call `finalizar` and does **not** clear the cookie. Account remains `CANCELACION_EN_PROGRESO` (frozen — new logins rejected, §7 A07). Returns `202`.
- Response bodies:
  - `200 OK`: `{ "estado": "COMPLETADA", "mensaje": "Su cuenta y sus datos personales han sido eliminados." }`
  - `202 Accepted`: `{ "estado": "PARCIAL", "mensaje": "No se pudo completar la eliminación en todos los sistemas. Vuelva a intentarlo en unos minutos." }`
- Status codes:
  - `200` / `202` — as above.
  - `400 Bad Request` — missing `passwordActual`, or `confirmacion` not exactly `"ELIMINAR_MI_CUENTA"` (`{"error": "Debe escribir exactamente ELIMINAR_MI_CUENTA para confirmar"}`).
  - `401 Unauthorized` — no/invalid `sl_jwt` cookie; or `passwordActual` incorrect (also the natural outcome for an already-`CANCELADA` account reached via a still-valid old JWT whose embedded email no longer... — no, see above: `CANCELADA` actually 404s via `findByEmail`, not 401; 401 is reserved for a genuinely wrong password against an existing, non-cancelled-away row).
  - `404 Not Found` — the email from a still-valid JWT no longer resolves to an account (either the pre-existing "cookie outlives account" edge case, or the account has already completed cancelación under a different, now-anonymized email — same underlying mechanism, not distinguished in the response, consistent with not leaking which case occurred).
  - `409 Conflict` — blocked by an active pedido/envío: `{"error": "No puede cancelar su cuenta mientras tenga pedidos o envíos en curso.", "pedidosBloqueantes": [12, 15]}` (pedido IDs belong to the caller themselves — not an IDOR disclosure).
  - `429 Too Many Requests` — new `cancelacionRateLimiter` (5/60s, same shape as `loginRateLimiter`/`rectificacionRateLimiter` — this endpoint also accepts a password guess with a distinguishable 401 vs. other outcomes, same oracle risk class as rectificación).

### 6.2 `PUT /auth/interno/usuarios/{email}/cancelacion/iniciar|revertir|finalizar` — new, internal-only

- Not reachable via `/api/**` — `authRoute()`'s existing `path("/api/auth/interno/**").negate()` predicate already excludes every sub-path under this prefix, including these three new ones; **no `GatewayConfig` change needed** for `auth-service` specifically (already true for the existing `GET`/`PUT .../email` endpoints).
- Auth: internal HMAC headers, `InternalAuthFilter`'s existing "everything under `/auth/interno/**` → `api-gateway` only" rule (matches on path prefix, not exact suffix) — **no filter code change**.
- `iniciar`: body `{ "passwordActual": "...", "confirmacion": "..." }` (confirmacion re-validated here too — never trust the gateway's own Bean Validation as the only check, defense in depth). `404`/`401` per §6.1.
- `revertir`, `finalizar`: no body. `404` if email no longer resolves (defensive; should not happen in the intended call sequence since `iniciar` already found the row).

### 6.3 `PUT /pedidos/interno/por-email/{email}/anonimizar` — new, internal-only

- Not reachable via `/api/pedidos/**` — already excluded by the existing `path("/api/pedidos/interno/**").negate()` predicate (matches any sub-path).
- Auth: falls into `ms-pedidos`'s existing default bucket ("everything else → `api-gateway` only") — no filter change.
- Response `200 OK`: `{ "cantidadAnonimizada": 3 }` (rows affected — `0` is a legitimate, non-error outcome for an account with no pedidos).

### 6.4 `PUT /pagos/interno/por-email/{email}/anonimizar` — new, internal-only

- **Not** automatically excluded — `pagosRoute()` has no `interno/**` predicate today (ms-pagos never had an internal-only endpoint before this design). **`GatewayConfig.pagosRoute()` must be updated** to add `.and(path("/api/pagos/interno/**").negate())`, mirroring `pedidosRoute()`/`enviosRoute()`/`authRoute()` exactly. Without this change, `PUT /api/pagos/interno/por-email/{any-email}/anonimizar` would be reachable by **any authenticated user**, who could anonymize any other user's payment records by editing the email in the URL — the identical IDOR-by-construction trap the acceso design already documented and closed for the other three services (`arco-acceso-personal-data.md` §1/§6 A01), reintroduced here if this exclusion is skipped.
- Auth: `ms-pagos`'s `InternalAuthFilter` already allows `api-gateway` for any path except `/pagos/webhook/flow` (confirmed by reading the actual filter, not the summary table in `internal-service-auth.md` which describes it as more narrowly per-path than it currently is) — no filter code change.
- Response `200 OK`: `{ "cantidadAnonimizada": 1 }`.

### 6.5 `POST /api/usuarios/me/oposicion` — new (Oposición)

- Auth: valid `sl_jwt` cookie, no role restriction, **no password re-authentication** — this is a reversible preference toggle with no destructive/irreversible consequence (unlike Cancelación or Rectificación's identity change), so step-up-auth is not warranted; a valid session is sufficient, consistent with the risk-proportionality principle already applied elsewhere in this codebase (e.g., `GET /api/usuarios/me/datos` needs no extra auth beyond a valid cookie either).
- Request body: `{ "oponerse": true }` (or `false`, to withdraw a prior objection — Ley 21.719 doesn't make this a one-way ratchet). Validation: `@NotNull Boolean oponerse`.
- Implementation: gateway calls `PUT /auth/interno/usuarios/{email}/oposicion` (body forwarded as-is). `auth-service` sets `oposicionProcesamiento = oponerse`, `oposicionRegistradaEn = now()` (always updated to reflect the latest decision date, even when toggling back to `false`).
- Response `200 OK`: `{ "oposicionProcesamiento": true, "oposicionRegistradaEn": "2026-08-28T10:00:00" }`.
- Status codes: `200` as above; `401` — no/invalid cookie; `404` — email no longer resolves (cookie-outlives-account, including a since-cancelled account); `400` — missing/non-boolean `oponerse`.
- **No rate limiter added** — unlike Cancelación/Rectificación, this endpoint carries no password, so it has no password-guessing-oracle risk; matches the existing precedent of no rate limiting on other non-credential-bearing authenticated mutations in this codebase.
- **Honesty requirement carried into the contract itself**: this endpoint's response and any user-facing copy must not claim this stops any specific kind of processing — because today, nothing is gated by it (§1). The correct framing, consistent with what this design actually does: "hemos registrado su oposición; hoy SmartLogix no realiza tratamiento de datos basado en interés legítimo distinto del necesario para prestar el servicio contratado, pero este registro queda disponible para cualquier tratamiento opcional que se incorpore en el futuro."

### 6.6 Extension to existing acceso/portabilidad response (small, mechanical)

`CuentaDTO`/`UsuarioInternoDTO` (both in `api-gateway` and `auth-service`) gain two new fields, `oposicionProcesamiento` (boolean, `false` if the underlying column is `null`) and `oposicionRegistradaEn` (nullable), so a user can verify their own recorded objection via `GET /api/usuarios/me/datos`/`/exportar` — otherwise the flag would be write-only, which is a weaker accountability posture than the rest of this design achieves elsewhere. No new endpoint; this is a field addition to an existing, already-versioned DTO.

## 7. Security requirements (OWASP Top 10 2021)

### A01 — Broken Access Control
- Identity for both new public endpoints is derived exclusively from the verified `sl_jwt` cookie — neither accepts a user/email identifier as a client-supplied parameter, closing the same IDOR class every prior ARCO+ cycle has closed.
- **The one genuinely new access-control surface this design introduces**: `ms-pagos`'s first-ever `/interno/**` endpoint. This is closed by the `GatewayConfig.pagosRoute()` route-exclusion (§6.4) — **this is the single most important implementation detail in this entire design to get right**, and must be verified by test (§8, criterion 9), not just asserted, exactly like the acceso design's own IDOR closure was.
- The blocking-check reads (`GET /pedidos/interno/por-email/{email}`, `GET /envios/interno/por-pedidos`) are **already** protected by the existing route exclusions from the acceso design — reused, not newly exposed.

### A02 — Cryptographic Failures
- `passwordActual` crosses the internal boundary twice now (rectificación's existing precedent, plus this new call) — same handling convention (never logged, §7 A09).
- The new random-password-hash-on-finalize (§4.1) is generated server-side from `UUID.randomUUID()`, never transmitted, never logged, encoded via the existing `BCryptPasswordEncoder(12)` bean — no new hashing scheme.
- No payment card data touched (`Pago.email` is the only field anonymized in `ms-pagos`; `flowToken`/`commerceOrder`/`monto` are untouched, and none of them were card data to begin with, per `COMPLIANCE_CL.md` §2).

### A03 — Injection
N/A. `anonimizarPorEmail` on both `OrderRepository` and `PagoRepository` are parameterized `@Modifying @Query` JPQL bulk updates (`UPDATE ... SET ... WHERE LOWER(email) = LOWER(:email)`), consistent with the existing `findByUserEmail` pattern — no string concatenation, no native SQL.

### A04 — Insecure Design (abuse cases — the load-bearing section for Cancelación)
- **Retry of a stuck cancelación**: by design, not an edge case to merely tolerate — the same endpoint IS the retry mechanism. Every step (state transition, blocking-check, anonymization, finalize) is idempotent: re-running `iniciar` on an already-`CANCELACION_EN_PROGRESO` account is a no-op state-wise; re-running the bulk `UPDATE`s a second time matches zero additional rows; re-running `finalizar` on an already-`CANCELADA` account can't happen because `iniciar` already 404s first (the email no longer resolves) — so `finalizar` is never reached twice for the same account.
- **Double-submit / concurrent requests**: two simultaneous calls to `POST /api/usuarios/me/cancelacion` from the same session both pass `iniciar` (idempotent transition, no unique-constraint conflict since `status` isn't unique), both re-run the blocking check and anonymization (harmless, idempotent), and at most one successfully calls `finalizar` first — the second's `finalizar` call would find the row already carrying the anonymized email under the *original* lookup key... **this is a real edge case requiring an implementation note**: `finalizar` must be looked up by the row's stable numeric `id` captured at `iniciar` time (passed through the internal call chain), not re-resolved by `email`, precisely because a concurrent successful `finalizar` may have already changed the email out from under a second in-flight request. This must not throw an unhandled exception (same class of bug already caught once in `internal-service-auth.md`'s QA feedback) — the second `finalizar` call finding an already-`CANCELADA` row by `id` should be treated as an idempotent no-op success, not an error.
- **Race with an in-flight write to `Pedido`/`Pago` during the transition window**: because the account remains `CANCELACION_EN_PROGRESO` (not yet `CANCELADA`) and the existing JWT is still technically valid (stateless — §7 A07), a still-authenticated session *could* create a new pedido during the brief window between the blocking-check passing and `finalizar` completing. This is why the blocking-check is **re-run on every call, not cached from a prior attempt** (§6.1, step 2) — a `202`-then-retry sequence will correctly re-discover and block on any pedido created in the interim, rather than blindly proceeding to anonymize data for an order that didn't exist at the time of the original check.
- **Password-guessing oracle**: same risk class and same mitigation as rectificación (`cancelacionRateLimiter`, 5/60s) — a stolen-but-valid cookie plus this endpoint's distinguishable `401` vs. other outcomes is a password oracle without it.
- **Oposición has no comparable abuse case**: no password, fully reversible, idempotent by construction (toggling to the same value twice is a no-op state-wise, though the timestamp does update — an intentional design choice so the *most recent* expression of the subject's preference is always the one on record, which is the legally correct behavior for a right that isn't a one-way ratchet).

### A05 — Security Misconfiguration
- New env var: none required beyond what already exists (`INTERNAL_SERVICE_SECRET`, `JWT_SECRET` are reused, not new). New Resilience4j config: `cancelacionRateLimiter` (three `application.properties` lines in `auth-service`, mirroring `rectificacionRateLimiter`'s existing three). No new ports, no new actuator exposure.
- The `pagosRoute()` change (§6.4) is a **security-critical configuration change**, not a routine one — flagged explicitly so it isn't treated as a low-risk one-line diff during review.

### A07 — Auth Failures
- **New behavior this codebase hasn't had before**: `AuthService.login()` must reject login when `status == "CANCELACION_EN_PROGRESO"` (checked *after* password verification, so the response only reveals this state to someone who already proved they know the correct password — same disclosure-timing discipline already used for rectificación's distinct error messages). A `CANCELADA` account needs no explicit login-rejection code: its `email` column no longer matches any credential a real user would submit, so `findByEmail` already fails it via the existing "Credenciales inválidas" path.
- **Session revocation — the decision, stated explicitly at the higher stakes this right carries.** This design does **not** add a JWT deny-list/Redis. Rationale: (a) the *account row itself* becomes unreachable by original email the moment `finalizar` runs — any endpoint that looks up state by email (every one in this codebase) will 404/degrade gracefully for a stale token exactly as already documented for rectificación, so the practical blast radius of "an old token is still cryptographically valid" is bounded to "can prove you once were this user," not "can still access this user's now-nonexistent/anonymized data"; (b) during the `CANCELACION_EN_PROGRESO` window specifically (the one window where the row *is* still reachable by original email and personal data hasn't fully moved yet), the new login-rejection check (above) closes the *new-session* vector, and the *existing-session* vector is explicitly bounded by the blocking-check-is-re-run-every-retry mitigation (A04) rather than by revocation; (c) building a deny-list store purely for this feature, when the residual risk is already substantially narrower than rectificación's already-accepted equivalent gap, would be new infrastructure (Redis, per `internal-service-auth.md`'s own explicit note that none exists in this stack) introduced for a materially smaller marginal benefit than its cost. This is a considered decision, not a punt — restated so a future reviewer doesn't need to re-litigate it without this reasoning in front of them.

### A08 — Software/Data Integrity
No deserialization of untrusted external input. All new internal calls carry the existing HMAC signature — no new signing mechanism, no new trust boundary shape.

### A09 — Logging/Monitoring
- **Must log** (in `auth-service`, mirroring the existing `"[ARCO+] Rectificación..."` convention): `"[ARCO+] Cancelación iniciada — email={}"`, `"[ARCO+] Cancelación revertida (pedidos/envíos activos) — email={}"`, `"[ARCO+] Cancelación completada — email original hash/id, no el email en texto plano tras anonimizar"` (once the email column is overwritten, log the row's stable `id`, not the now-anonymized value, so the audit trail is still traceable to a specific account without re-introducing the erased PII into logs), `"[ARCO+] Oposición registrada — email={}, oponerse={}"`.
- **Must NOT log**: `passwordActual` (either endpoint), `confirmacion` value is harmless to log (it's a fixed literal the user typed back, not a secret, but there's no reason to log it either — omit for minimalism), the full anonymized/pre-anonymized personal data payload.

### A10 — SSRF
N/A. Same fixed, operator-configured internal URLs as every other ARCO+ endpoint.

## 8. Chilean compliance touchpoints

This design implements `COMPLIANCE_CL.md` §4.2's "Cancelación / supresión" and "Oposición" rows — once merged, both should move to `✅ implementado`, citing the merging commit/PR, per §5 of that document.

- **Ley 21.719, derecho de cancelación/supresión**: satisfied via anonymization rather than physical row deletion for `auth-service`/`ms-pedidos`/`ms-pagos` — defensible under the "deber de seguridad + proporcionalidad" framing already used in `COMPLIANCE_CL.md` §3, since anonymized data (no longer identifying the data subject) falls outside the scope of "datos personales" the law is written to protect, while still preserving the minimum operational/audit trail (order totals, payment amounts and status, timestamps) that a legitimate accounting/dispute-resolution retention basis would justify keeping. **Known, explicitly-flagged limitation, not silently accepted**: `Pedido.clienteNombre`/`destino` are **not** anonymized by this design, because they describe the PYME's *own end customer* — a different data subject whose ARCO+ rights are not exercised by the PYME account holder's own cancelación request. If SmartLogix's actual customer base includes that end-customer as a data subject SmartLogix itself has direct obligations to, that is a separate, not-yet-designed feature (there is no login/account for a PYME's end customer in this codebase today — flagged in Open Questions).
- **Ley 21.719, derecho de oposición**: this design's honest position, restated for the compliance doc's own row: *"Mecanismo implementado (`POST /api/usuarios/me/oposicion`, `User.oposicionProcesamiento`); actualmente no gatilla ningún cambio de comportamiento porque no existe tratamiento opcional/de interés legítimo activo en el sistema — queda como registro auditable y punto de verificación obligatorio para cualquier tratamiento opcional futuro."* This is a materially different, more honest status than a bare `✅ implementado` would imply on its own — the compliance doc's entry should carry this caveat verbatim or in substance, not just the checkmark.
- **§4.4 Logging y auditoría**: the new audit lines (§7 A09) are direct improvements to the same checklist row every prior ARCO+ cycle has improved.
- **Retention (§4.4)**: this design is itself a retention-limiting control — cancelación is the mechanism by which personal data stops being retained indefinitely. No new retention question is introduced by the *columns* added (`status`/timestamps are metadata about the retention/erasure event itself, not new personal data).
- **Ley 21.663 (gestión de riesgos / incident-relevant logging)**: the audit trail this design adds (cancelación requested/blocked/completed, oposición registered) is exactly the kind of "quién, qué, cuándo" reconstruction capability `COMPLIANCE_CL.md` §4.4 and §3 already call for — a burst of cancelación attempts against a single account, or a cancelación immediately followed by unexpected activity on the same session, is now a detectable, loggable signal it wasn't before.

## 9. Acceptance criteria

### Cancelación (`POST /api/usuarios/me/cancelacion`)
1. Logged in as user A with no pedidos at all: correct password + correct confirmation string → `200`, `estado: "COMPLETADA"`, `Set-Cookie` clears `sl_jwt` (`Max-Age=0`), a subsequent login attempt with A's original email/password fails (`401`, credentials no longer match any row).
2. Same as #1, but `confirmacion` is `"eliminar_mi_cuenta"` (wrong case) or `"ELIMINAR"` (wrong string) → `400`, no state change (`users.status` in `auth_db` remains unchanged, verify via a follow-up login still succeeding).
3. Same as #1, but `passwordActual` is wrong → `401`, no state change.
4. User B has exactly one pedido with `status = "PENDIENTE"`: correct password + confirmation → `409`, `pedidosBloqueantes` includes that pedido's ID, `users.status` reverts to (or remains) `"ACTIVA"` (verify via a follow-up login succeeding normally), and **no** row in `pedidos_db`/`pagos_db` was modified.
5. User C has one pedido with `status = "ENTREGADO"` and its linked envío `status = "ENTREGADO"`: cancelación succeeds (`200`) — proves the terminal-status allowlist doesn't over-block a genuinely completed order.
6. User D has one pedido with `status = "PAGO_ANULADO"` (failed payment, terminal) and no envío at all (Saga never fired): cancelación succeeds — proves a failed-payment pedido with no downstream shipment doesn't block.
7. **IDOR abuse case (critical, ms-pagos specifically):** `PUT /api/pagos/interno/por-email/{any-email}/anonimizar` requested directly through the gateway with a valid cookie for an unrelated user → `404` (no matching route) — proves the new `pagosRoute()` exclusion (§6.4) was actually added, not merely designed.
8. From within `smartlogix-net`, `ms-pagos:8086/pagos/interno/por-email/{any-email}/anonimizar` with no internal-auth headers → `401`.
9. **Retry-to-completion**: stop `ms-pagos` before calling the endpoint (with a user who has ≥1 pedido eligible for cancelación, i.e., not blocked). First call → `202` (pedidos anonymized, pagos not — verify `pedidos_db` row's `user_email` is already `"USUARIO_ELIMINADO"` while `pagos_db`'s row is untouched), `users.status` is `"CANCELACION_EN_PROGRESO"`, login for that account now fails distinctly (account frozen). Restart `ms-pagos`, call the same endpoint again with the same body → `200`, `pagos_db` row now anonymized too, `users.status` is `"CANCELADA"`.
10. During the frozen window from #9 (before the retry), attempt to log in with the account's original credentials → rejected (not the generic "Credenciales inválidas" — a distinct account-frozen outcome, verified by log output/response distinguishing this from a simple wrong-password case at the `auth-service` level, even if the public login endpoint's user-facing message stays generic for enumeration-safety).
11. **Double-submit/concurrency**: two simultaneous, correctly-authenticated cancelación requests for the same unblocked account → both eventually return `200`/`202` (no unhandled `500`), the account ends in `CANCELADA` exactly once, and `pedidos_db`/`pagos_db` rows are not double-processed or corrupted (row counts match expectations, no duplicate anonymization side effects).
12. **Rate limiting abuse case:** 6 rapid attempts with wrong `passwordActual` within 60 seconds → the 6th returns `429`.
13. No `sl_jwt` cookie → `401`, request never reaches `CancelacionController`'s body logic.
14. Log output for a completed cancelación contains no plaintext `passwordActual`, no full JWT, and references the account by stable `id` (not its now-anonymized or original email) in the completion log line.
15. Regression: `GET /api/usuarios/me/datos`, `PUT /api/usuarios/me/email`, `GET /api/pedidos`, `POST /api/pedidos`, the full Saga flow, and `POST /api/pagos/crear`/`GET /api/pagos/{id}` all continue to work unchanged for accounts not undergoing cancelación — in particular, the new `pagosRoute()` predicate change must not shadow any existing legitimate `/api/pagos/**` path.

### Oposición (`POST /api/usuarios/me/oposicion`)
16. Logged in as user A: `{"oponerse": true}` → `200`, `oposicionProcesamiento: true`, non-null `oposicionRegistradaEn`; a follow-up `GET /api/usuarios/me/datos` shows the same values under `cuenta`.
17. Same user, `{"oponerse": false}` → `200`, flag flips back, timestamp updates to the new call's time (not the original) — proves this isn't a one-way ratchet.
18. Missing/non-boolean `oponerse` → `400`.
19. No `sl_jwt` cookie → `401`.
20. **IDOR abuse case**: no client-supplied identifier of any kind influences whose flag is set — same as every other ARCO+ mutation endpoint's core anti-IDOR property.
21. **Honesty/non-overclaim check (documentation-level acceptance criterion, not just code)**: confirm that no code path in `notification-service`/`NotifyStep`/anywhere else was modified to branch on `oposicionProcesamiento` — this criterion exists specifically to prevent a well-intentioned but incorrect implementation from accidentally gating transactional shipping/order notifications on this flag, which would be a Ley 21.719 compliance error (blocking contract-necessary communication under the wrong legal basis), not a fix.
22. Static/code-level check: `CuentaDTO`/`UsuarioInternoDTO` expose `oposicionProcesamiento`/`oposicionRegistradaEn` and no other new field carries the underlying `User.password`.

## 10. Open questions

1. **`Pedido.status` has no automated path to `"ENTREGADO"` in the current codebase** (verified: no code sets this value anywhere outside a hypothetical manual/admin process that doesn't exist yet — only `"PENDIENTE"` on creation, `"PAGADO"` on payment confirmation, `"CONFIRMADO"`/`"CANCELADO"` inside the Saga's `CreateOrderStep`, and whatever literal string Flow's `estadoFlow` produces via `marcarPagoFallido`). This means, in practice, an account whose only pedido ever reached `"PAGADO"` may never see its status allowlist-match a terminal value through any automated process today, and would need its linked *envío* to reach `"ENTREGADO"`/`"CANCELADO"` instead (which **is** reachable via the existing `PATCH /envios/{id}/status`, presumably an ops-driven action outside this codebase's automated flows) to unblock cancelación. This is a pre-existing gap in the order/shipment lifecycle, not something this design introduces or should silently paper over — flagged so the orchestrator/human understands why the blocking condition might feel stricter than expected until that lifecycle gap is separately addressed.
2. **`Pedido.clienteNombre`/`destino` (the PYME's own end-customer data) are explicitly out of scope for this design** (§8) — if SmartLogix's product direction ever gives that end customer their own rights against SmartLogix directly (not mediated through the PYME account), that is a materially different, larger feature (would need its own identity/consent model for a data subject who has no account in this system today) and should not be assumed solved by this cycle.
3. **No admin/support path to force-resolve a permanently-stuck `CANCELACION_EN_PROGRESO` account** (e.g., if `ms-pagos` is down for an extended period and the user never retries). Given this codebase has no admin tooling for ARCO+ processes at all today, this is consistent with existing scope limits, but worth flagging as a real operational gap before a production deployment with real users, per `COMPLIANCE_CL.md`'s own disclaimer about engineering-level vs. legal-certified compliance.
4. **Frontend gap, now spanning three ARCO+ cycles.** Neither this design nor the prior two propose a UI beyond the read-only "Mis datos" page. A destructive, high-stakes action like Cancelación arguably needs a UI *more* than the read-only rights do (a raw `curl`/API-only path to permanently erase one's own account is a worse user experience than for Acceso/Rectificación) — worth prioritizing a small frontend design for at least Cancelación's confirmation flow before treating ARCO+ as practically, not just technically, complete.
5. **Whether `oposicionProcesamiento` should also suppress the account from any future analytics/BI export** (not notification-service, but e.g. a hypothetical future admin dashboard aggregating usage patterns) is left undecided — no such feature exists today to design against, consistent with this document's own "no speculative abstraction" stance; flagged so a future design touching analytics explicitly checks this flag rather than rediscovering the need from scratch.
